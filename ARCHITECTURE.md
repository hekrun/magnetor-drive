# Architecture

```
Browser (static HTML/JS/CSS, embedded in the binary)
   │  JSON/HTTP, session cookie + CSRF header
   ▼
internal/server   – routing, auth middleware, security headers, error mapping
   ├─ internal/auth      – owner login (PBKDF2), in-memory sessions, login throttling
   ├─ internal/drive     – virtual-path file store (the only code touching user files)
   └─ internal/torrents  – .torrent creation + seeding via anacrolix/torrent
internal/config   – environment configuration
cmd/magnetor-drive – wiring
```

## Data layout

```
$MAGNETOR_DATA_DIR/
  files/      user files (the only tree the UI can browse)
  torrents/   <infohash>.torrent files and records.json (never browsable)
```

## Drive store

All API paths are *virtual*: slash separated, relative to `files/`. `drive.Clean` rejects `..`, backslashes and NUL; every component is validated and `Lstat`-checked so symlinks are never followed (and are hidden from listings and skipped when copying). Errors are mapped to path-free messages, so server paths never reach clients. Uploads stream to a temporary file and are hard-linked into place, so existing files are never overwritten and partial uploads never appear. Move/copy of a folder into itself is rejected.

## Authentication

A single owner is configured via environment variables. The password is hashed in memory with PBKDF2-HMAC-SHA256 (stdlib); sessions are random tokens stored hashed in memory, delivered in an `HttpOnly`, `SameSite=Strict` cookie. State-changing requests require an `X-CSRF-Token` header. Failed logins are throttled per client IP (5 per 15 minutes). Sessions are lost on restart.

## Torrents

`Create` builds the metainfo from the selected path with the library, saves the `.torrent` under `torrents/`, and adds it to a lazily created client whose per-torrent storage is the **parent directory of the selected item inside `files/`**. The library therefore reads pieces from the original files: no second copy exists. Data download is disabled for these torrents so remote peers can never write into user files. On add, all pieces are verified in the background (`verifying` → `seeding`).

A fingerprint (relative names, sizes, mtimes) is stored at creation. Any rename/move/delete/upload/copy/mkdir through the API that overlaps a torrent's source invalidates it immediately; changes made behind the app's back are detected when seeding is (re)started. Invalid torrents stop seeding and must be regenerated by choosing *Create torrent* again.

## Preview and downloads

Only an allowlist of types (images, PDF, audio, video, plain text) is served inline, with `nosniff` and a sandboxing CSP; everything else is `attachment`, so uploaded HTML/SVG cannot run script on the Drive origin.
